# Server Setup, Run Scripts, and Bug Fixes (Linux/Godot port)

This documents how to run the whole server stack headless on Linux, the
(confusing) password system, and the bugs fixed while getting account →
character → enter-world → server-authoritative movement + mob following working.

## 1. Running everything

```bash
# one-time: create the runtime databases from the MoMReborn baseline
./run_servers.sh --setup        # or: python3 setup_databases.py --worldname=TestDaemon

# every time: start the whole stack in the background
./run_servers.sh

# stop everything
./stop_servers.sh
```

`run_servers.sh` launches each server as a **background process** (unlike the old
`start_servers.sh`, which opens a GUI terminal window per server and is useless
over SSH / headless). Logs go to `logs/<ServerName>.log`; the spawned world
process logs to `logs/ZoneCluster0.txt`. PIDs are tracked in `logs/servers.pids`.

Ports: **Master 2002**, **GM 2003**, **World 2008**, **Proxy `ws://localhost:9000`**
(the Godot client connects to the proxy). These come from `projects/mom.cfg` and
`serverconfig/TestDaemon.py`.

### Dependencies (modern Python 3)
`requirements.txt` pins ancient Python-2-era versions. On Python 3.11 the stack
actually runs with:
```
pip install "Twisted>=22,<24" sqlobject pyopenssl service_identity bcrypt pyasn1
pip install --no-deps autobahn txaio hyperlink      # proxy WebSocket bridge
```
(`autobahn`'s optional `py-ubjson`/`cbor` serializers fail to build and aren't
needed — the proxy speaks JSON over text frames.)

### Headless integration test
`tools/proxy_integration_test.py` drives the proxy exactly like the Godot client
(register → login → world account → character → enter world), then moves the
player and logs whether the nearest mob follows. Handy for regression-checking
the gameplay path without launching Godot.

## 2. The three passwords (this trips everyone up)

There are **three independent credentials**. This is legacy MoM design, not a bug:

| Password | Where it comes from | Used for |
|----------|--------------------|----------|
| **Master account password** | Auto-generated at registration (or now **chosen by you**) and stored in `data/master/master.db` | Logging into the Master server (`username-Player`) |
| **World access password** (shared) | `serverconfig/<World>.py` → `PLAYERPASSWORD` (default `mmo`) | Gate to *create* a world account on that world |
| **World account password** (per player/world) | Auto-generated by the world when you create a world account | Logging into the world server to play |

**The "assigned password you must remember" is the master account password.**
It was previously a random 8-letter string (`GenPasswd().upper()`).

**New:** you can now choose your own master password at registration. Type a
password (4+ chars) in the login password box before clicking Register; leave it
blank to get a random one (legacy behaviour). See `perspective_submitKey` in
`mud_ext/masterserver/main.py` and `handle_register` in `ClientProxy.py`.

Accounts and characters **do persist** across restarts (they live in the SQLite
DBs under `data/` and `minions.of.mirth/data/worlds/...`). The character DB is
keyed by unique character name, so the same name can't be reused across accounts.

## 3. Bugs fixed in this pass

| Area | File | Problem → Fix |
|------|------|---------------|
| **Mob AI (caster mobs)** | `mud/world/mobspells.py:125` | `sorted(..., cmp=SpellSort)` is Py2-only → `TypeError` every tick, so any mob with healing spells **crashed on spawn and never ran AI**. Now uses `functools.cmp_to_key`. |
| **Mob AI (aggro)** | `mud/world/tactical.py:213` | `c.mob.detached` crashed when a party slot had no spawned mob, aborting the aggro pass. Now skips `None` mobs. |
| **Mob equipment** | `mud/world/mob.py:866` | `dict.itervalues()` (Py2) → `.values()`. |
| **Re-enter world** | `mud/worldserver/charutil.py` | Second entry hit `UNIQUE constraint failed: character.name` ("Transfer Error"). Added `RemoveInstalledCharacter()` so install is idempotent. |
| **Entity facing** | `minions-port/gameplay_view.gd` | Yaw was **left-right mirrored** converting Torque Z-up axis-angle to Godot Y-up. Negated the reconstructed yaw. (Cosmetic — does not affect position/following.) |
| **DB setup** | `setup_databases.py` | A 0-byte `master.db` from a failed run "exists", so creation was skipped and the Master server crashed (`no such table: user`). Now validates the DB has the `user` table. |
| **Log spam** | `mud/server/app.py:218` | `####perspective_call` printed on **every** PB call (~20/sec while moving). Gated behind `MUD_DEBUG_PB=1`. |

## 4. Coordinate space, tick rate, interpolation (server-authoritative)

**Coordinate space — no position bug.** Server (Torque) is **Z-up**; Godot is
**Y-up**. The conversion `godot = (x, z, -y)` (and inverse `server = (x, -z, y)`)
is a *proper rigid rotation* applied identically to the player and every entity,
so distances and relative positions are exactly preserved. A mob that chases in
server space chases identically in Godot space. (Verified numerically and by
running the live server.) The only coordinate bug was the **facing/yaw mirror**,
now fixed; it never affected following.

**Tick rates (all server-authoritative):**
- Client → server input: **20 Hz** (`INPUT_SYNC_INTERVAL = 0.05`)
- Server player movement sim: **20 Hz**, 8 u/s (`stubsim._MOVE_INTERVAL`, `_PLAYER_MOVE_SPEED` — matches client `MOVE_SPEED`)
- Server NPC chase movement: **20 Hz** (`stubsim._updateMovement`)
- Server world tick (mob.tick/battles): **2 Hz** (`theworld.tick`, `callLater(.5)`)
- Server AI re-target (aggro): **every ~2 s** (`mob.tacticalTimer`)
- Server visibility (canSee): **every 2 s** (`stubsim._updateCanSee`)
- Proxy → client entity snapshots: **~10 Hz** (`ClientProxy` entity sync)
- Client entity interpolation: `lerp` at `ENTITY_INTERPOLATION_SPEED = 8` — **already present**

So: the server owns movement (20 Hz), replicates at ~10 Hz, and the Godot client
already interpolates remote entities between snapshots. You do **not** need to add
more interpolation. NPC movement speed in the stub is currently a flat 5 u/s
(`StubSimObject.moveSpeed`) rather than the mob's real `move` stat, so mobs trail
a faster player — acceptable for combat testing; raise it or wire it to
`mob.move` if you want them to keep pace.

## 5. Known remaining rough edges (not yet fixed)

- **Disconnect cleanup:** when a client drops, the world keeps ticking the player
  briefly and logs `DeadReferenceError: Calling Stale Broker` (`player.py` mind
  callRemotes). Cosmetic spam; a proper fix removes the player on broker death.
- **Entity snapshot range:** the proxy only sends mobs within **50 units**
  (`ClientProxy._on_entity_snapshot`) and the client caps display range — fine for
  combat, but distant mobs won't appear. Tunable.
- **`/tmp/enterworld_debug.log`:** `charutil.InstallCharacterBuffer` appends debug
  output to `/tmp` on every enter. Harmless, but noisy.
- **NPC chase speed** is a flat `StubSimObject.moveSpeed = 5.0`; not yet wired to
  the mob's real `move` stat (see §4).
